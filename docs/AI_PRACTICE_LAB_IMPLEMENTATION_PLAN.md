# AI Practice Lab — Implementation Plan (Phase 1: Product Shell)

**Status:** Phase 1 complete and verified live. **Update (same session, later):** Decision #2 below ("Judge0 deferred") was revisited and reversed — see the note after the Decisions list. Real execution now exists for eligible challenges via a self-hosted Judge0.
**Scope:** Product shell — nav entry, overview, challenge library, and a full Monaco-based challenge workspace with Run/Evaluate/Submit. Real execution for single-file, no-dependency Python challenges via self-hosted Judge0; everything else (RAG/Agents, multi-file, needs-dependencies) behind an honest mock. No Docker sandbox, no AI-based evaluation.

See [`AI_PRACTICE_LAB_ARCHITECTURE.md`](./AI_PRACTICE_LAB_ARCHITECTURE.md) for the technical reference (schemas, API surface, component map, the Judge0 self-hosting setup and its cgroup-v2 workaround). This document covers *why* the scope landed where it did and what's still deferred.

## Existing architecture discovered

Repo investigation (see the full session that built this feature) found more reusable infrastructure than a from-scratch build would assume:

- **Backend layering** — `models/` (Beanie ODM Documents) → `schemas/` (Pydantic DTOs) → `repositories/` (query logic) → `services/` (business logic) → `api/routes/` (thin FastAPI routers, one file per concern, bare prefixes like `/roadmaps`, not `/api/...`) → registered in `main.py`. Practice Lab follows this exactly — `models/practice_challenge.py`, `practice_submission.py`, `practice_progress.py`; matching `schemas/`, `repositories/`, `services/` files; three routers (`practice_challenges`, `practice_submissions`, `practice_progress`).
- **A real Redis + `arq` async worker already runs in production** (`apps/backend/worker/`, Redis via root `docker-compose.yml`) — not Celery/RQ/Dramatiq. Not wired into Practice Lab yet, but it's the natural home for real queued execution in a future phase, and removes most of the "stand up a queue from scratch" risk that phase would otherwise carry.
- **`services/code_sandbox_service.py` already runs real, isolated code today** via Judge0/RapidAPI, used in Interview Prep. A genuine secure-execution precedent — deliberately **not** wired into Practice Lab in Phase 1 (see Decisions below), but documented as the clear next step for simple, single-file `python-for-ai` challenges.
- **`providers/base.py` + `providers/registry.py`** — the existing "swap the implementation behind one seam" pattern (used for the Gemini/Groq/OpenAI/Ollama AI provider chain) — this is the model `services/execution_service.py`'s `ExecutionService` Protocol follows.
- **Frontend** — React 18 + TypeScript, `apps/web/src/features/<feature>/` convention (many small, single-purpose component files rather than a few large ones), TanStack Query for server state, a thin per-feature `xApi.ts` over a shared axios client, and a mature design-token system (`Card`, `Badge`, `Button`, `Menu`, `Drawer`, `Toast`, `Tabs` — the last built new for this feature, generalizing a pattern from the Community redesign).
- **Nothing pre-existing**: no Monaco anywhere in `apps/web`, no `Tabs.tsx` primitive, no `scripts/` seeding precedent, no admin CMS.

## Decisions

1. **Scope = Phase 1 shell only.** The full blueprint (Docker sandbox, RAG/Agent evaluators, XP economy, AI tutor, admin CMS) is genuinely weeks of infrastructure work. Phase 1 delivers the complete product shell — everything a student sees and does except real code execution — behind one clean, swappable `ExecutionService` interface, so later phases are additive, not a rewrite.
2. **Judge0 reuse: initially deferred, then adopted (self-hosted).** The original call was to leave `code_sandbox_service.py` unwired in this pass, to keep execution behavior uniform (all mock) rather than a confusing "this challenge is real, this one isn't" mix. Revisited later the same session: the mix turned out to be fine as long as it's honestly labeled per-response (`executed`/`engine` on every `ExecutionResultDto`, rendered via `ExecutionStatusBanner`) rather than a single page-wide claim — a user opening an eligible challenge sees "ran for real," an ineligible one sees "preview," and that's arguably more honest than mocking everything uniformly once *some* of it can be real. Landed as self-hosted Judge0 (`docker-compose.yml`'s `judge0-*` services) rather than RapidAPI, avoiding an external paid dependency — see the Architecture doc for the setup and a real cgroup v1/v2 compatibility issue that came up and its fix.
3. **Run and Evaluate are stateless — no MongoDB writes.** This matches the blueprint's own semantics ("Run: no permanent score," "Evaluate: does not necessarily finalize the submission") and means Phase 1 needs no execution-job polling UI at all — `MockExecutionService` responds synchronously, so Run/Evaluate are plain request/response mutations. **Submit is the only action that persists** a `Submission` and updates `UserPracticeProgress`.
4. **Nothing is ever "solved."** Every test outcome Phase 1 can produce is `"not_run"` — never `"passed"`/`"failed"` (the type stays a 3-way union so a real engine needs no schema change later). The Challenge Library's status filter is therefore **Unsolved / Attempted only**, no "Solved" option — that would be a fabricated claim about code that never ran. Progress tracks only `challengesAttempted` and `totalSubmissions`, never XP or skill scores.
5. **Seed content = Python for AI + RAG + Agents, 14 challenges.** Generic ML/classification was skipped for this pass — it needs real datasets and sklearn to be meaningful, and there's no sandbox for that yet. RAG and Agents are the platform's actual differentiator per the blueprint.

## MVP definition of done (met)

A student can: open Believe.ai → navigate to AI Practice Lab → browse/search/filter challenges → open a challenge → read the scenario/requirements/sample tests → edit permitted files in Monaco → Run → see honest preview output (never a fabricated pass) → Evaluate → Submit → see the attempt in Submission History → return to Overview and see real progress (`challengesAttempted`, `totalSubmissions`, "Continue practicing") reflecting that submission.

The platform also, verified live via network inspection (not just code review): hidden test definitions never appear in any API response; user code never executes inside the FastAPI process itself (eligible challenges execute inside the isolated Judge0 sandbox; everything else executes nowhere — the mock service does no `exec`); a genuinely-wrong submission for an eligible challenge really fails (`0/2 tests passed`, not a fabricated pass); MongoDB is the only application database (Judge0's own internal Postgres is a third-party dependency's implementation detail, not Believe.ai's data — see the Architecture doc); existing Believe.ai auth and design system are unchanged.

## Explicitly out of scope (future phases)

Docker-sandboxed execution for RAG/Agent/ML challenges (needs real dependencies Judge0 can't provide); Redis-queued (`arq`) execution jobs for that; RAG/Agent/ML evaluators; ML/classification track content; XP, streaks, skill-tree scoring; "solved" status; AI tutor and hints backend; admin CMS (seeding is a one-off dev script, `scripts/seed_practice_challenges.py`); Community/Notes/Roadmap cross-feature integration; contests/leaderboards; multi-language execution (Judge0 path is Python-only so far, matching the seed content); execution rate-limiting (nothing costly to throttle yet, though real sandbox time now makes this worth revisiting sooner than before).
